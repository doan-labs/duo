# Store

Stage 2 MVP: [scope amendment](stage-2-mvp.md). Required now: choose a separately
hosted developer catalog, verify and install its immutable release, and open it
without rebuilding the simulator. Curated shelves, ranking, reviews and commerce
remain roadmap. Existing basic Apps/Updates controls are optional retained work.

**Implemented (stages 2–5):** explicit catalog selection and Refresh, verified
GET/OPEN/UPDATE/remove, staging while a session runs, restore/retry, DEV row
removal, and a locally built `index.json` (`scripts/build-app.ts`). **Roadmap,
not implemented:** CI-published catalogs, icon size variants, release notes in
the index, hourly catalog polling, Update All, badges, an auto-update toggle
and Software Update. Sections below describing those are the original plan.

The App Store app becomes real. It reads one index, installs bundles, and shows
updates. No backend, no accounts.

The first-party catalog and bundles will be served as static files from
`https://duo.doan-labs.com`; final paths and the hosting provider remain open.
The CDN layout below is an artifact layout, not yet a public route assignment.
Native clients use a configured absolute catalog URL. Independently hosted
developer catalogs remain supported. See [web.md](web.md#deployment) for
cache policy and deployment verification.

## CDN layout

```
cdn/
  index.json                        mutable, Cache-Control: max-age=60
  apps/<id>/<version>+<hash>/release.json  immutable: manifest + build metadata + hashed file list
  apps/<id>/<version>+<hash>/app.html      immutable: the whole app document, script and styles inline
  apps/<id>/<version>+<hash>/icon-1024.png immutable; the builder emits this one size
  shell/latest.json                 Tauri updater, see updates.md
  shell/<version>/*.dmg|.msi|.AppImage
```

The release identity is `version+hash` (progress/contract.md §1.2): a rebuild
that changes bytes is a new identity, so nothing under a published identity
ever changes and CI refuses to write into an existing folder. A release is
`release.json`, one `app.html` and the icons. Publish the catalog only after
the complete release is available. The desktop bundle ships preinstalled
releases in its own assets and installs them offline on first boot, once,
behind a seed marker so an uninstall is not undone; the web deployment serves
the same files under `/preinstalled/`, a network source like any other.

## index.json

Generated by CI from the releases on `main` (progress/contract.md §1.5):
every published release identity is listed, newest first, with its host
requirement and the hash of its `release.json`, so an older shell can pick the
newest release it can run and the download can be verified.

```json
{
  "apps": {
    "dev.example.tides": {
      "name": "Tides", "lane": "community",
      "author": "Ada", "repo": "...", "summary": "...", "category": "Weather",
      "widgets": ["small"], "permissions": ["geolocation"],
      "releases": [
        { "release": "1.2.0+9f3ab21c", "sdk": "1.4.0", "bytes": 412000, "note": "Tide tables offline",
          "sha256": "<release.json>" },
        { "release": "1.1.0+02cc7e10", "sdk": "1.2.0", "bytes": 398000, "note": "…", "sha256": "…" }
      ]
    }
  }
}
```

The shell fetches it once at boot and on explicit Refresh; there is no polling
(`packages/shell/runtime/catalog.ts`). Offline, the last copy
in local storage stands. `bytes` is the measured size of `app.html`; the
budget is set after Notes is built (progress/contract.md, open items).

## Shelf

Today, Games, Apps, Updates, Search, the real tabs. Today is a curated list in
the repo (`packages/apps/TODAY.md`, a list of ids). Apps is the index sorted
by lane then name, with the Community ribbon on community entries. Search is
name and summary, client side.

## Install

GET → progress → OPEN, as the current fake button does, but the progress is the
real fetch. The sequence is progress/contract.md §4.4, under a per-app lock:
`release.json` verified against the index, validation and the compatibility
check, `app.html` streamed with progress and a size bound, its hash verified
against the release, icons, then one IndexedDB transaction writing the release
and the `installed` record together, whose completion is the commit point.
The icon appears in the first free cell of the inner display. Interrupted
before commit: nothing is written and GET returns. A boot sweep deletes
unreferenced release records older than ten minutes. Baked apps show OPEN and
never GET.

Requires: the Store picks the newest release whose `sdk` the running shell's
host SDK satisfies under full caret semantics, evaluated against the current
host every time. The app's bundled kit version is not the host requirement.
With no compatible release, the row reads "Requires a newer platform version"
and offers Software Update on desktop or Reload on web; a shell version is
named only when the index maps the requirement to one. An open browser tab can
still run an old shell.

## Updates tab

Compare installed versions with compatible catalog releases. Each newer entry is a row
with the version, the size and the release note, which is the first line of
the app's `CHANGELOG.md` (CI copies it into the index). Update All at the top.
The App Store icon badges the count; Settings badges when a shell update waits.

Auto-update is a toggle in Settings, on by default. A downloaded update sits
as `candidate` and activates when no tab holds a session lease for the app,
never while a view is running; the row reads "Updates when Notes closes"
meanwhile. A candidate that failed to start twice is `failedVersion`: the tab
shows "Retry update" and never reactivates it on its own
(progress/contract.md §4.5 and §4.6).

## Uninstall

Long-press on the home screen, Remove App, the real two-step; the first pass
puts Remove on the installed row in the Store and adds the long-press after.
Order (progress/contract.md §4.9), under the app lock: mark the record
`removing` and bump its generation so every tab revokes its views, wait for
leases to clear, delete release bytes, app data, checkpoints, recovery and
legacy copies and widget snapshots, then the record, keeping the non-data
marker that prevents a legacy reimport. Baked apps offer Remove from Home
Screen only; preinstalled isolated apps uninstall fully and reinstall from the
local source on desktop, from the network on the web.
